# 制約下動的状態遷移システム（UCD-F）汎用設計書 — Universal Core v2.3.0

> **本書の位置づけ**
> v1.0.0 系の3設計書（`UCD-F`, `UCD-F_ABC`, `Py_UCD-F_ABC`）を検証し、
> 「特定の実行環境・ドメインに依存しない**抽象コア**」と「差し替え可能な**プロファイル**」に
> 層分離して再構築した汎用版である。
> 既存の WebGPU / WGSL / WebRTC / ABC-32bit パッキング等は、本書では
> コアの規範ではなく **参照プロファイル（Reference Profile）** として位置づける。

## 表記法

本書の要求水準は RFC 2119 に準拠し、次の日本語表現に英語キーワードを併記する。

| 表現 | キーワード | 意味 |
| --- | --- | --- |
| 〜しなければならない | **MUST** | 準拠に必須 |
| 〜してはならない | **MUST NOT** | 準拠上の禁止 |
| 〜すべきである / 〜すべきでない | **SHOULD** / **SHOULD NOT** | 正当な理由がある場合のみ逸脱可 |
| 〜してよい / 〜しなくてよい | **MAY** | 任意（許可であり、要否の指示ではない） |

条件付きの要求には、**「〜する場合 MUST」**の形式を用いる。当該条件に該当しない場合、その要求は適用されない。

数式・記号は §2 で定義する。用語は §11 を正とする。

| --- | --- | --- |
| 1 | 形式モデルが版ごとに不整合（`UCD-F`=12要素 `(S,A,C,B,D,M,Q,ε,V,P,H,L)` ／ `UCD-F_ABC`=10要素 `(S,A,C,B,D,M,ε,V,T,N)` ／ `Py_UCD-F_ABC`=11要素 `(U,S,A,C,B,D,M,ε,V,T,N)`）。核タプルが安定しない。 | 「確定状態を決定するか否か」の単一基準で**確定核5要素**と**観測層3要素**へ再区分し、他は能力として分離（§2）。 |
| 2 | 「Universal」を名乗るが WebGPU/WGSL/WebRTC/32bit-ABC が本文に直書きされ、非対応環境で破綻。 | 実装技術をすべて**実行プロファイル**へ退避（§7）。コアは技術中立。 |

| 6 | ABC/VIF という特定ドメインの動態モデルがコアに埋め込まれ、他ドメインへ転用不能。 | VIF を**汎用 Dynamics 契約**の一写像、ABC を**参照ドメインプロファイル**へ格下げ（§6, §8）。 |

## 1. アーキテクチャ全体像（4層モデル）

UCD-F は「厳しい資源制約を、決定論・データ指向・段階的詳細度によって技術的優位へ転換する」ためのフレームワークである。汎用性を担保するため、責務を次の4層に分離する。

```
┌─────────────────────────────────────────────────────────┐
│ L4  ドメインプロファイル (Domain Profile)                 │  例: ABC/VIF, 粒子, 群衆, 経済…
│     状態スキーマ・遷移規則・Dynamics写像                   │  （差し替え可能）
├─────────────────────────────────────────────────────────┤
│ L3  実行プロファイル (Execution Profile)                  │  例: WebGPU, Python/wgpu, CPU参照
│     具体的な計算/描画/転送バックエンドへの束縛             │  （差し替え可能）
├─────────────────────────────────────────────────────────┤
│ L2  機構契約 (Mechanism Contracts)                        │  メモリ/空間索引/スケジューラ/入力/
│     能力ごとの抽象インターフェース                         │  露出/出力/予測/転送/履歴（抽象）
├─────────────────────────────────────────────────────────┤
│ L1  抽象コア (Abstract Core)                              │  不変の形式モデルと
│     形式モデル・決定論・状態遷移の意味論                   │  状態遷移の意味論（規範・不変）
└─────────────────────────────────────────────────────────┘
```

### 設計原則（Invariants）

**1. 決定論優先（Determinism-First）** — 次の二段階に分離して定義する。

- **再現性（Reproducibility）**: 同一実装・同一**再生同一性**（§4.9.2）・同一初期シード・同一入力列からは、常にビット等価な状態列が再生されなければならない（**MUST**）。全適合性レベルで必須。実行ごと・並列分割ごとに結果が揺れてはならない（**MUST NOT**、§2.3 順序独立性）。
- **実装間ビット等価（Cross-implementation Bit-equivalence）**: 異なる実装・異なるハードウェア間でのビット等価は、§4.9.4 の数値決定論（固定小数点等）を採用した実装のみが主張できる（**MAY**）。Full レベルでは必須（**MUST**）。

> この分離により、単一ノード用途で浮動小数点を用いる実装も Core/Standard に準拠できる一方、その実装は実装間ビット等価を主張してはならない（**MUST NOT**）。**主張の有無は再生同一性の構成を変える**（§4.9.2）。

**2. データ指向（Data-Oriented）** — 状態は識別可能なフィールド集合として表現する。物理表現（SoA/AoS/ビットパック）は実装裁量とするが、論理スキーマは実装から独立して定義しなければならない（**MUST**）。

**3. 段階的詳細度（Graceful Degradation / LOD）** — 資源負荷に応じ精度・更新頻度・実体化度を動的に落としてよい（**MAY**）が、コアの意味論を破壊してはならない（**MUST NOT**）。適応は次の2種に厳密に区別する。

- **シミュレーション適応**（確定状態に影響する精度・更新頻度・実体化）: 判断入力を**確定状態および権威化された入力**（§5）に由来するものに限定しなければならない（**MUST**）。実行時計測（実時刻・CPU 温度・実測フレーム時間等）および確定状態外の観測者情報（表示専用カメラ等）に依存してはならない（**MUST NOT**）。
- **表示適応**（描画解像度・視錐台カリング等、出力のみ）: 実行時計測 `M(t)` および実行時カメラに依存してよい（**MAY**）。確定状態に影響してはならない（**MUST NOT**）。

> 観測に基づく最適化（観測外カリング・精度昇格等）は**シミュレーション適応**である。観測領域を判断に用いる場合、それは §4.4 の**観測者状態**として確定状態の一部でなければならない（**MUST**）。

**4. 明示的制約（Explicit Constraints）** — メモリ・権限・計算資源の制約を暗黙に踏み越えてはならず（**MUST NOT**）、モデルの一級要素 `C` として扱わなければならない（**MUST**）。

**5. 可逆性（Reversibility）** — 記録された（再生同一性, 初期シード, 入力列）からの**再計算のみ**で、任意の確定 Tick に到達できなければならない（**MUST**）。全状態の逐次永続化を一次履歴としてはならない（**MUST NOT**）。チェックポイント（§4.9.3）は再生コストを削減する派生キャッシュとして保持してよい（**MAY**）。

## 2. 抽象コア形式モデル（L1・不変）

### 2.1 確定核（Determination Core・5要素）

確定状態の軌跡を決定する要素のみで構成する。準拠システムはこれらをすべて備えなければならない（**MUST**）。

$$\text{Core} = (S,\; A,\; C,\; D,\; \varepsilon)$$

| 要素 | 名称 | 意味（技術中立） |
| --- | --- | --- |
| $S$ | State（状態） | 各エンティティの論理状態。フィールド集合として定義される固定スキーマ、または非実体領域の要約分布。 |
| $A$ | Action（入力） | 状態を変化させ得る外部入力の列。ユーザー入力・権威化された環境入力・ネットワーク入力・**観測者状態**（§4.4）を含む。 |
| $C$ | Constraint & Core（制約と遷移中核） | 資源・権限の制約集合と、それを尊重する状態遷移規則（TR: Transition Rule）。 |
| $D$ | Dynamics（力学） | 状態変化に付与される動的性質（勢い・励起・蓄積・相互作用）を定義する契約（§6）。 |
| $\varepsilon$ | Environment（環境） | 実行環境の制約係数と、外部から収穫・権威化された環境ノイズ（§5）。 |

### 2.2 観測層（Observation Layer・3要素）

確定状態を**一切変更しない**要素群。これらが確定状態に影響してはならない（**MUST NOT**）。核とは別レイヤとして扱う。

$$\text{Obs} = (B,\; M,\; V)$$

| 要素 | 名称 | 意味 | 契約 |
| --- | --- | --- | --- |
| $B$ | Bank（露出制御） | 権限と観測状態に応じ、どの状態をどの観測者へ露出するかを規定。 | §4.5 |
| $M$ | Metrics（計測） | 負荷・品質指標。**表示適応の入力源**。シミュレーション適応の判断に用いてはならない（**MUST NOT**、§1 原則3）。 | §4.1（表示 LOD）, §4.6（出力） |
| $V$ | View / Output（出力） | 確定状態の外部表現（描画・ログ・エクスポート）への写像。 | §4.6 |

> **区分基準について**: v2.0.0 は `B`・`M` を核に含めつつ「確定状態を変えない」と規定し、同じ理由で `V` を核外へ降格させていた（基準の不一致）。v2.1.0 以降は「**確定状態を決定するか否か**」という単一基準で再区分し、状態を決めない `B`・`M`・`V` を観測層へ統一した。これにより核は5要素で安定する。
>
> **観測層と観測者状態の違い**: 観測*層*（B/M/V）は状態を変えない。一方、シミュレーション適応の判断に使う**観測者状態**（観測領域・注視点）は確定状態を変えるため、観測層ではなく**確定核の入力 $A$** に属する（§4.4）。両者を混同してはならない（**MUST NOT**）。

### 2.3 状態遷移の意味論

$$S_{t+1} = C_D\big(S_t,\; A_t,\; \varepsilon_t\big)$$

- $D$ は $C$ を**パラメータ化する時不変の契約**であり、Tick ごとの入力ではない。上式はこれをカリー化により明示する。
- $C_D$ は**純粋関数**でなければならない（**MUST**）。同一入力から同一出力を返し、副作用（I/O・描画・乱数の暗黙参照）を持ってはならない（**MUST NOT**）。
- 乱数が必要な場合、$\varepsilon_t$ に含まれる**明示シード**からの決定論的擬似乱数（例: PCG 系ハッシュ）のみを用いなければならない（**MUST**）。
- 時間は離散 **Tick**（整数 ID）で進む。複数の演算主体が存在する構成では、全主体が同一 Tick ID に対し同一の $C_D$ を適用しなければならない（**MUST**）。
- 観測層 $(B, M, V)$ は遷移式に現れない。これらが確定状態へ影響してはならない（**MUST NOT**、§2.2）。

#### 順序独立性（Order Independence）

$C_D$ は、同一 Tick 内で評価されるエンティティの**評価順序に依存してはならない**（**MUST NOT**）。すなわち:

- §4.2 の階層伝播が定める**世代間の順序**を除き、同一世代内では**任意の評価順序・任意の並列分割**に対して同一結果を返さなければならない（**MUST**）。
- 順序に依存する簡約（非結合・非可換な演算の累積）を、順序が保証されない実行文脈で用いてはならない（**MUST NOT**、§6）。

> **なぜ独立の要件として必要か**: $C_D$ が**純粋関数であることは、並列簡約の順序独立性を含意しない**。純粋であっても、浮動小数点加算のような非結合演算を不定順序で累積すれば結果は揺れる。
>
> 本要件がなければ、§4.2 のデータ再配置（**MAY**）・§4.3 の稠密化（**MAY**）・並列実行はいずれも評価順序を変えるため、原則1 の再現性を**実装の運任せ**にしてしまう。順序独立性は、これらの最適化を安全に許可するための前提条件である。検証は §9 の**順序独立性検証**による。

### 2.4 能力（Capabilities）— 核・観測層の外側

v1.0.0 で核タプルに混在していた要素は、**任意能力**として分離する。準拠実装は必要なものだけを実装してよい（**MAY**）。実装要否は §9 の適合性レベルが定める。

| 能力 | 記号 | 機構契約 | v1.0.0 での扱い |
| --- | --- | --- | --- |
| Quantization / LOD | $Q$ | §4.1 | 核要素。実体は Memory 機構に従属 |
| Layout Schema | $L$ | §3.2 | 核要素。実体はスキーマ・コンパイラ契約 |
| Hierarchy | $H$ | §4.2 | 核要素。状態スキーマの一制約 |
| Time Dilation | $T$ | §4.3 | 核要素。スケジューラの一戦略 |
| Prediction | $P$ | §4.7 | 核要素。探索は本番タイムライン外の任意能力 |
| Network | $N$ | §4.8 | 核要素。転送は任意拡張 |

これにより核は版・環境によらず不変となり、旧3版（`UCD-F` / `UCD-F_ABC` / `Py_UCD-F_ABC`）の形式不整合を解消する。

## 3. 論理状態スキーマ（L1↔L2 境界）

### 3.1 スキーマ・ファースト

状態 $S$ は、**論理スキーマ**として実装から独立に定義されなければならない（**MUST**）。スキーマは以下を宣言する。

- フィールド名、論理型（列挙・整数・固定小数点・正規化実数 等）、値域、意味。
- どのフィールドが**遷移で単調非減少となるか**（蓄積型フィールド、§6）。
- どのフィールドが **LOD で精度を落としてよいか**（可縮フィールド）。

物理的表現（ビット幅・パッキング・SoA/AoS・GPU/CPU 常駐）は**実行プロファイルの裁量**である。§8.1 の「32bit ABC パッキング」は、この論理スキーマの一具体化にすぎない。

### 3.2 スキーマ・コンパイラ契約（能力 $L$）

実装は、論理スキーマからメモリレイアウトとアクセサ（パック／アンパック）を生成する仕組みを備えるべきである（**SHOULD**）。生成物は次を保証しなければならない（**MUST**）。

- アクセサのラウンドトリップ等価（`unpack ∘ pack` が恒等写像）。
- LOD 段階間の変換（低精度↔高精度）が明示的かつ決定論的であること。

### 3.3 スキーマ・バージョニング

論理スキーマは**バージョン識別子**を持たなければならない（**MUST**）。スキーマまたは遷移規則 $C_D$ を変更した場合、識別子を更新しなければならない（**MUST**）。過去の入力ログの再生時は §4.9.2 の再生同一性検査に従う。

## 4. 機構契約（L2・抽象インターフェース）

各機構は**抽象契約**として定義し、実装は実行プロファイルで束縛する。ここでは具体技術（WGSL / Morton 順序 / WebRTC 等）を規定せず、**満たすべき性質**のみを述べる。

### 4.1 メモリ & 量子化（Memory / Quantization）

- **契約**: 論理スキーマに対する読み書きを提供し、GC／アロケーションのフレーム内スパイクを回避する。固定容量プールを用いるべきである（**SHOULD**）。
- **LOD**: 演算・通信・実体化の精度を動的に段階制御する。段階遷移はコア意味論を保存しなければならない（**MUST**）。区分は §1 原則3 に従う。
  - **シミュレーション LOD**: 判断入力は確定状態・権威化入力（観測者状態を含む）由来に限る（**MUST**）。同一入力から同一の段階選択となり、再現性を保存する。
  - **表示 LOD**: 実行時計測 $M(t)$ や実行時カメラからの距離に依存してよい（**MAY**）。確定状態に影響してはならない（**MUST NOT**）。
- **観測外カリング（Lazy Instantiation）**: **確定観測領域**に含まれないエンティティは、個別演算を停止しマクロ要約分布へ圧縮してよい（**MAY**）。観測時に定数時間相当で再実体化できるべきである（**SHOULD**）。
  - **確定観測領域の定義**: **全観測者**（§4.4）の観測者状態が定める観測領域の**合併（union）**とする。
  - 本カリングは実体化度を変える＝**確定状態を変える**ため、**シミュレーション適応**である。判定に用いる観測領域は確定状態でなければならず（**MUST**）、表示専用カメラで駆動してはならない（**MUST NOT**）。
  - 複数の**演算主体**（§4.4）が存在する構成では、この合併が**全演算主体で一致していなければならない**（**MUST**）。各演算主体が自分のローカル観測者の領域のみで判定すると、圧縮対象が演算主体ごとに異なり確定状態が分岐する。§4.4 に従い、全観測者の観測者状態を入力列として共有・権威化する。
    - 本要件は「全観測者が同じ場所を観測すること」を意味しない。各観測者の領域は自由であり、**その合併の計算結果が全演算主体で一致する**ことを要求する。
  - 描画のための視錐台カリング・遮蔽カリングは**表示適応**であり、§4.6 で実行時カメラに基づき行ってよい（**MAY**）。両者を混同してはならない（**MUST NOT**）。
- **密度上限時の強制要約化**: 局所密度が閾値を超えた場合、優先度の低い個体を要約分布へ吸収し、資源上限内で演算を継続すべきである（**SHOULD**）。これにより無制限な個体増加でも破綻しない。優先度の判定入力は確定状態由来に限る（**MUST**）。
- **階層型ストレージ（Hot / Warm / Cold）**: 常時参照される作業集合を高速メモリ（Hot）に、待機状態を主記憶（Warm）に、長期退避分を外部ストレージ（Cold）へ段階配置してよい（**MAY**）。Cold への退避・読み戻しはメイン更新をブロックしないチャンク単位の非同期 I/O とすべきである（**SHOULD**）。配置は物理的関心事であり、確定状態に影響してはならない（**MUST NOT**）。

### 4.2 空間索引 & 階層（Spatial Index / Hierarchy）

- **契約**: 近傍・可視範囲・相互作用対象を平均 $O(1)$〜$O(\log n)$ で抽出する。手法（空間ハッシュ、一様グリッド、木構造、空間充填曲線順序等）はプロファイル裁量。
- **列挙方式の宣言**: 実装は探索半径 $r$ と、**厳密列挙**または**近似列挙**のいずれかを宣言しなければならない（**MUST**）。
  - **厳密列挙**を宣言する場合: $r$ 以内の近傍を漏れなく列挙しなければならない（**MUST**）。セル境界をまたぐ近傍の取りこぼしは本要件の違反である。
  - **近似列挙**を宣言する場合: 取りこぼし率の上限を宣言しなければならない（**MUST**）。近似の判定は決定論的でなければならず（**MUST**）、実行時計測に依存してはならない（**MUST NOT**）。
- **階層伝播**: 親子連結を持つドメインでは、親の確定後に子を評価する順序（トポロジカル整列）で評価し、世代間の伝播遅延を生じさせてはならない（**MUST NOT**）。**この世代間順序は §2.3 の順序独立性の唯一の例外**であり、同一世代内の順序は依然として結果に影響してはならない（**MUST NOT**）。
- **局所性最適化**: 索引順に実データを周期的に再配置し、参照局所性を高めてよい（**MAY**）。再配置は物理的関心事であり、確定状態に影響してはならない（**MUST NOT**）。**本許可は §2.3 の順序独立性が満たされていることを前提とする**。順序独立性を満たさない遷移で再配置を行えば再現性が壊れる。

### 4.3 スケジューラ & 時間制御（Scheduler / Time Dilation）

- **契約**: Tick 進行と、エンティティ／領域ごとの更新頻度配分を管理する。
- **局所時間拡張**: 変動の大きい領域を高頻度、静穏な領域を低頻度で更新してよい（**MAY**）。頻度を決める判断入力は**確定状態由来**（例: 変動量 $\Delta$）に限らなければならず（**MUST**）、実測フレーム時間等に依存してはならない（**MUST NOT**）。これにより同一入力から同一の更新スケジュールとなり、再現性を保存する。
- **稠密化**: 実行対象を密なリストへ圧縮し、遊休スレッドを削減してよい（**MAY**）。稠密化は評価順序を変えるため、**本許可は §2.3 の順序独立性が満たされていることを前提とする**。

### 4.4 入力パイプライン（Action Ingestion）

#### 用語の区別

| 用語 | 定義 |
| --- | --- |
| **観測者（Observer）** | 露出・観測の主体（ユーザー、カメラ、外部システム）。1つの演算主体が**複数の観測者を保持しうる**。 |
| **演算主体（Compute Subject）** | $C_D$ を実行して確定状態を進める主体（ノード／プロセス）。 |

両者は独立の概念であり、混同してはならない（**MUST NOT**）。露出制御（§4.5）は**観測者**ごと、確定状態の一致（§4.1, §4.8）は**演算主体**ごとに論じる。

#### 契約

- 入力を低アロケーションで取り込み、Tick へ決定論的に割り付ける。固定容量リングバッファを用いるべきである（**SHOULD**）。
- **シード化と記録**: すべての非決定的入力（乱数・環境ノイズ・センサ値）は、$C_D$ へ渡る前にシード化され、$\varepsilon_t$ の一部として確定し、履歴へ記録されなければならない（**MUST**）。これは単一ノード構成を含む**全構成で必須**である。
- **観測者状態（Observer State）**: 観測領域・注視点等、観測者に紐づく値を**シミュレーション適応**（§4.1 観測外カリング、§8.1 精度昇格 等）の判断に用いる場合、それらは**権威化された入力 $A$ として確定状態の一部**でなければならない（**MUST**）。
  - 表示専用のカメラ等、確定状態外の値をシミュレーション適応に用いてはならない（**MUST NOT**）。
  - 複数の演算主体が存在する構成では、**全観測者**の観測者状態を入力列として共有し、§5 の権威化を経なければならない（**MUST**）。これにより全演算主体が同一の確定観測領域（合併）を算出する。
  - 観測者状態を**表示適応にのみ**用いる場合、確定状態に含めなくてよい（**MAY**）。この場合は §4.6 の実行時カメラとして扱う。
- **権威化**: 複数の演算主体が同一の確定状態を共有する構成では、加えて §5 の権威化手続きを経なければならない（**MUST**）。単一演算主体の構成では権威化を行わなくてよい（**MAY**）。

### 4.5 露出制御（Bank）

- **契約**: **観測者**（§4.4）ごとに、確定状態のどの部分集合を露出するかを決定する。
- 露出制御は確定状態を**読み取るのみ**であり、変更してはならない（**MUST NOT**）。露出の可否が遷移結果に影響してはならない（**MUST NOT**）。
- 権限モデル（観測者の識別・権限集合・既定の拒否／許可）を宣言しなければならない（**MUST**）。既定は**拒否**とすべきである（**SHOULD**）。
- 露出判定は、確定状態と観測者権限のみの関数でなければならない（**MUST**）。同一状態・同一権限からは常に同一の露出集合が得られる。
- 非露出フィールドは、出力（§4.6）およびネットワーク送出（§4.8）の**いずれの経路からも漏出してはならない**（**MUST NOT**）。要約分布へ圧縮された領域についても、露出制御は個別実体と同等に適用しなければならない（**MUST**）。

> Bank は単なる表示フィルタではなく**信頼境界**である。予測（§4.7）が非露出情報を用いて介入を決定すると、その結果が観測者へ間接的に情報を漏らし得る（サイドチャネル）。予測の入力は、当該観測者に露出された情報に限定すべきである（**SHOULD**）。
>
> **残存リスク（設計上の既知の帰結）**: **観測者状態**（§4.4）は確定核の入力であり、Bank の管轄外である。シミュレーション適応に観測領域を用いる構成では、観測者状態が全演算主体へ共有されるため、**他の観測者がどこを観測しているかは秘匿されない**。観測領域そのものの秘匿が要件となるドメイン（対戦型等）では、観測に基づくシミュレーション適応を採用しないか、観測領域の粒度を粗くして情報量を削るなど、**ドメイン設計側で対処しなければならない**（**MUST**）。露出制御では解決できない。

### 4.6 出力アダプタ（View / Output）

- **契約**: 確定状態を外部表現（描画・ログ・エクスポート）へ写像する。コアに対して**読み取り専用**であり、状態を変更してはならない（**MUST NOT**）。
- 出力対象は §4.5 の露出制御を通過した部分集合に限らなければならない（**MUST**）。
- **表示適応**: 描画解像度・視錐台カリング・遮蔽カリング等は、実行時計測 $M(t)$ および実行時カメラに基づき決定してよい（**MAY**）。これらは確定状態に影響してはならない（**MUST NOT**）。§4.1 の観測外カリング（シミュレーション適応）とは別物である。
- 大量エンティティの可視化では、中間オブジェクトを介さない直接束縛や不要描画の除外等で、アロケーションと過描画を抑制すべきである（**SHOULD**）。
- 出力は副作用であるため、再現性検証（§9）の対象外としてよい（**MAY**）。

### 4.7 予測 & 探索（Prediction）

- **契約**: 本番タイムラインを汚染せず、確定状態の複製上で未来を試行する。探索は確定状態を変更してはならない（**MUST NOT**）。
- **探索範囲**: 探索対象を**影響範囲**（介入地点から波及し得る範囲）に限定し、範囲外を静的近似として扱うべきである（**SHOULD**）。
- **計算予算**: 実装は 1 Tick あたりの予測処理に**時間ないし演算量の予算上限を宣言**しなければならない（**MUST**）。予算超過分は後続 Tick へ繰り越さなければならず（**MUST**）、単一 Tick 内で予算を超えて占有してはならない（**MUST NOT**）。これにより主更新ループのレートが予測処理から保護される。
- **反映**: 探索結果の本番反映は、入力 $A$ として明示的な確定点でのみ行わなければならない（**MUST**）。反映された介入は履歴（§4.9）へ記録されなければならない（**MUST**）。
- **探索起点**: 一次履歴からの再計算、またはチェックポイント（§4.9.3、実装する場合）を起点として用いる。
- 探索の入力は §4.5 の但し書き（サイドチャネル）に従う。

### 4.8 ネットワーク（Network・任意能力）

- **契約**: 複数の演算主体で空間・状態を分担する場合の同期。
- 同期方式は、**入力列を共有する決定論的ロックステップ**または**権威サーバ方式**のいずれかを選ばなければならない（**MUST**）。ローカル確定状態の全体をブロードキャストしてはならない（**MUST NOT**）。
- 決定論的ロックステップを選ぶ場合、全演算主体は同一の**再生同一性**（§4.9.2）を持たなければならない（**MUST**）。不一致の主体は参加を拒否されなければならない（**MUST**）。
  - 実装間ビット等価を主張する構成では、**プロファイルの相違は許容される**（**MAY**）。異なるプロファイル（例: A と B）が同一の再生同一性を持ち、いずれも実装間ビット等価（§4.9.4）を満たすなら、混成メッシュを構成してよい。この場合、プロファイルを参加条件にしてはならない（**MUST NOT**）。
  - 実装間ビット等価を主張しない構成では、実装識別子が再生同一性に含まれる（§4.9.2）ため、**異なる実装は参加できない**。これは意図された制限である。
- **観測者状態の共有**: シミュレーション適応に観測領域を用いる構成（§4.1, §4.4）では、共有する入力列に**全観測者の観測者状態を含めなければならない**（**MUST**）。これを共有しなければ確定観測領域の合併が主体ごとに異なり、確定状態が分岐する。
  - 観測者状態を表示適応にのみ用いる構成では、共有しなくてよい（**MAY**）。不要な情報露出を避けるため、共有すべきでない（**SHOULD NOT**）。
- レイテンシ吸収のため、楽観的実行と巻き戻し再計算（ロールバック）を用いてよい（**MAY**）。巻き戻しは §4.9 の履歴に依存する。
- 送出データは §4.5 の露出制御を通過しなければならない（**MUST**）。
- トポロジ（P2P / DHT / 空間分割 / 権威）はプロファイル裁量である。

### 4.9 履歴 & 決定論（History / Determinism）

#### 4.9.1 一次履歴

- **契約**: 時間遡行と再計算の基盤。一次履歴は次の3点で構成しなければならない（**MUST**）。
  1. **再生同一性**（§4.9.2）
  2. **初期シード**
  3. **入力列**（ユーザー入力・権威化された $\varepsilon_t$・観測者状態・介入、すべて Tick ID 付き）
- 確定状態の逐次永続化を一次履歴としてはならない（**MUST NOT**）。コストが状態量 × Tick 数に比例し、可逆性の要件（原則5）を満たすために不要である。
- 任意の確定 Tick へは、一次履歴からの再計算のみで到達できなければならない（**MUST**）。

#### 4.9.2 再生同一性と実装メタデータ

一次履歴は次の2種の識別情報を記録しなければならない（**MUST**）。両者を混同してはならない（**MUST NOT**）。

**(a) 再生同一性（Replay Identity）— 一致が必須**

再生結果を左右する要素。記録された値と再生側の値が一致しない場合、**再生を拒否しなければならない**（**MUST**）。黙って再生してはならない（**MUST NOT**）。

*常に含める項目:*

| 項目 | 理由 |
| --- | --- |
| 論理スキーマ版（§3.3） | フィールド構成が変われば状態表現が変わる |
| 遷移規則 $C_D$ 版 | 遷移が変われば同一入力から別の軌跡になる |
| Dynamics 契約版（§6） | 減衰則等の変更が軌跡を変える |
| 数値表現（固定小数点フォーマット等） | 丸め挙動が変われば結果が変わる |

*適合性に依存する項目:*

| 構成 | 実装識別子（プロファイル＋実装版）の扱い |
| --- | --- |
| **実装間ビット等価を主張しない**（浮動小数点可。Core / Standard の既定） | 再生同一性に**含めなければならない**（**MUST**） |
| **実装間ビット等価を主張する**（数値決定論を採用。Full では必須） | 再生同一性に**含めてはならない**（**MUST NOT**） |

> **なぜ対称にする必要があるか**:
> - **主張しない構成で含めなければ**: 原則1 の再現性は「**同一実装**」でのみ保証される。実装識別子を検査しなければ、別実装（別の浮動小数点丸め）で生成されたログの再生を拒否できず、**再現できない再生を黙って受理して誤った結果を返す**。
> - **主張する構成で含めれば**: プロファイル A のログをプロファイル C で再生する基準実装照合（§7.3, §9）が「同一性不一致 → 再生拒否」となり**実行不能**になる。ビット等価な A + B 混成メッシュ（§4.8）も禁止されてしまう。実装間ビット等価とは「**プロファイルが変わっても結果が一致する**」という主張そのものであり、プロファイルは**変わってよい軸**でなければならない。

**(b) 実装メタデータ（Implementation Metadata）— 記録のみ、一致検査の対象外**

再生結果を左右しない、または (a) に含まれない付帯情報。監査・障害解析・環境特定に用いる。

| 項目 | 用途 |
| --- | --- |
| 適合性レベル（§9） | 主張された適合範囲の記録 |
| ホスト環境（OS・ハードウェア等） | 監査・障害解析 |
| プロファイル識別子・実装版 | 実装間ビット等価を主張する構成において、生成元の記録（検査には用いない） |

- 版を跨ぐ再生が必要な場合、明示的なログ移行（マイグレーション）を経なければならない（**MUST**）。移行は新しい再生同一性の下で新規ログとして扱う。

#### 4.9.3 チェックポイント（派生キャッシュ・任意）

一次履歴のみでの再生は Tick 数に比例したコストを要するため、実装はチェックポイントを保持してよい（**MAY**）。**全適合性レベルで任意**であり、以下は**実装する場合**に適用される。

- チェックポイントは特定 Tick における確定状態の完全な複製であり、**一次履歴から再生成可能な派生キャッシュ**として扱わなければならない（実装する場合 **MUST**）。権威を持たせてはならない（**MUST NOT**）。
- 破棄しても正しさが失われてはならない（**MUST NOT**）。破棄時は一次履歴からの再計算で復元する。
- 記録間隔を宣言しなければならない（実装する場合 **MUST**）。間隔 $k$ に対し、任意 Tick への到達コストは最悪 $O(k)$ に抑えられる。
- 再生同一性を継承しなければならない（実装する場合 **MUST**）。再生同一性が一致しないチェックポイントは無効として破棄しなければならない（**MUST**）。

> チェックポイントは**最適化であって仕様上の前提ではない**。可逆性（原則5）・蓄積フィールドの巻き戻し（§6）・探索起点（§4.7）は、いずれも一次履歴からの再計算のみで成立しなければならない（**MUST**）。チェックポイントはその高速化にすぎない。

#### 4.9.4 数値決定論

- **再現性**（原則1）は、単一実装内で同一の数値挙動が得られれば満たされる。浮動小数点を用いてよい（**MAY**）。
  - ただし浮動小数点を用いる場合、**§6 の原子演算制約**が適用される。浮動小数点加算は非結合であるため、順序が保証されない文脈で累積してはならない（**MUST NOT**）。これに違反すると、単一実装内であっても実行ごとに結果が揺れ、再現性そのものが失われる。
  - 浮動小数点を用いる構成は実装間ビット等価を主張してはならず（**MUST NOT**）、実装識別子を再生同一性へ含めなければならない（**MUST**、§4.9.2）。
- **実装間ビット等価**（原則1）を主張する実装は、浮動小数点の非決定的な丸め・演算順序への依存を排除し、固定小数点等のビット決定的演算を用いなければならない（**MUST**）。数値表現は再生同一性へ記録しなければならない（**MUST**）。
- 複数の異種ハードウェアが同一の確定状態を共有する構成（§4.8 の決定論的ロックステップ）では、実装間ビット等価が必須である（**MUST**）。

## 5. 環境エントロピーの収穫・正規化・権威化（$\varepsilon$）

外部環境のノイズをシミュレーション入力へ取り込む場合、決定論を破壊しない手続きを踏まなければならない（**MUST**）。

1. **収穫（Harvest）**: 外部信号（デバイス負荷、センサ値、外部 API の変動等）を独立プロセス／デーモンで取得し、メイン更新を阻害しないべきである（**SHOULD**）。
2. **正規化（Normalize）**: 時間ローリング平均等で恒常的な偏り（常時飽和・常時無入力）を抑え、相対的な変動のみを抽出すべきである（**SHOULD**）。
3. **シード化・記録**: 収穫値は $\varepsilon_t$ として Tick へ確定し、履歴へ記録しなければならない（**MUST**、§4.4）。**全構成で必須**。
4. **権威化（Authorize）**: 複数の演算主体が同一の確定状態を共有する構成では、各主体がローカル収穫値を直接演算へ混入してはならない（**MUST NOT**）。合意された単一の値（例: 選出されたリーダーによる「Tick N の確定エントロピー」）としてのみ注入しなければならない（**MUST**）。単一演算主体の構成では権威化を行わなくてよい（**MAY**）。
5. **拡散（Diffuse・任意）**: 過剰なエントロピーを隣接主体へ拡散し、系全体のマクロ均衡を保ってよい（**MAY**）。

シミュレーション適応に観測領域を用いる構成では、権威化の対象に**観測者状態**（§4.4）を含めなければならない（**MUST**）。収穫値の**意味付け**（どの信号を Dynamics のどの外因へ写すか）は L4 ドメインプロファイルの責務である（§8.3）。

## 6. Dynamics 契約（$D$・L2）

`Dynamics` は「状態変化に付与する動的性質」の**抽象契約**であり、具体モデルはドメインが与える。$D$ は確定核の要素（§2.1）であるため、本契約は **Core レベルから必須**である（§9）。

| 概念 | 一般的意味 | 要件 |
| --- | --- | --- |
| **Potential**（勢い） | 変化の方向と大きさのポテンシャル | 量子化可能でなければならない（**MUST**） |
| **Excitation**（励起） | 一時的・可逆な励起量 | 減衰則を定義すべきである（**SHOULD**） |
| **Accumulation**（蓄積） | 長期・不可逆な累積（劣化・疲労の一般化） | 遷移において単調非減少でなければならない（**MUST**）。減少は**一次履歴からの再計算による巻き戻し**（§4.9.1）経由でのみ生じてよい（**MAY**） |
| **Interaction**（相互作用） | 近傍間の伝搬・衝突解決 | 並行更新時の競合を回避しなければならない（**MUST**）。手段は下記の制約に従う |

- 相互作用を持たないドメインは、Interaction を空として宣言してよい（**MAY**）。
- Dynamics 契約はバージョン識別子を持ち、変更時に更新しなければならない（**MUST**、§4.9.2）。

### 6.1 相互作用の競合回避と決定論

> **競合（data race）の回避と決定論は別問題である。** 原子演算はレースを防ぐが、**適用順序の非決定性は防がない**。この区別を誤ると、レースフリーかつ純粋でありながら実行ごとに結果が揺れる実装が生まれる。

| 手段 | 順序依存性 | 許可条件 |
| --- | --- | --- |
| **ダブルバッファ**（ヤコビ反復等） | 読み書きを分離するため**順序独立** | 常に用いてよい（**MAY**） |
| **原子演算** | 適用順序が**非決定的** | **結合律と交換律を満たす演算に限り**用いてよい（**MAY**） |

- 原子演算を用いる場合、その演算は**結合律・交換律を満たさなければならない**（**MUST**）。整数加算（法 $2^n$ を含む）・XOR・min / max 等がこれに該当する。
- **非結合な演算に原子演算を用いてはならない**（**MUST NOT**）。とりわけ**浮動小数点加算**は非結合であり（$(a+b)+c \neq a+(b+c)$）、原子的に累積すると同一実装・同一入力でも実行ごとに結果が変わり、**原則1 の再現性（全レベル MUST）が破壊される**。
- 上記いずれの手段も、§2.3 の**順序独立性**を満たさなければならない（**MUST**）。数値解法（例: ヤコビ反復）の選択は機構・プロファイルの裁量だが、決定論的なマクロ挙動を保証しなければならない（**MUST**）。

> **注**: v1.0.0 の **VIF（Velocity / Intensity / Fatigue）** は、本契約の (Potential, Excitation, Accumulation) への一具体写像である。VIF はコアではなく、ABC ドメインプロファイル（§8）が提供する Dynamics 実装として扱う。

## 7. 実行プロファイル（L3）

同一の抽象コアを、複数バックエンドへ束縛する。プロファイルは各機構契約（§4）の具体実装を提供し、適合性（§9）を宣言しなければならない（**MUST**）。

### 7.1 参照プロファイル A: ブラウザ / WebGPU

- **計算**: WebGPU Compute Shader（WGSL）。空間索引に空間充填曲線（Morton）順序＋GPU ソート、周囲 27 セル探索により厳密列挙（§4.2）を実現。データ再配置パスで局所性最適化。
- **数値**: **Full 適合（実装間ビット等価）を主張する構成では**、確定状態に関わる演算から浮動小数点を排除し、固定小数点（16.16 等）を用いなければならない（**MUST**、§4.9.4）。Standard 以下に留まる構成では浮動小数点を用いてよい（**MAY**）が、その場合は実装識別子が再生同一性に含まれる（§4.9.2）。表示専用の演算は常にこの限りでない。
- **相互作用**: 密集領域の解決はダブルバッファ（Ping-Pong）によるヤコビ反復を基本とする。原子演算を用いる場合、整数加算・XOR・min/max 等の結合的演算に限る（**MUST**、§6.1）。
- **メモリ**: ビットパック SoA を GPU Storage Buffer に常駐、固定容量プール。
- **履歴**: 一次履歴とチェックポイントを GPU 内リングバッファで保持し、CPU-GPU 間 I/O を回避。
- **出力**: 二段遮蔽カリング＋間接ディスパッチ／間接ドロー（CPU は発行のみ）。これは表示適応（§4.6）であり、§4.1 の観測外カリングとは別パスである。
- **予測**: 木探索を独立 Compute Pipeline へオフロード、差分追跡＋計算予算による分割実行。
- **転送**: WebRTC P2P メッシュ（空間トポロジ認識ルーティング、任意）。観測者状態を用いる構成では入力列へ含めて共有（§4.8）。

### 7.2 参照プロファイル B: Python エコシステム（`wgpu-py` 基盤）

- **ユーザー API**: テンソル演算ベースの制約付き DSL（遅延評価グラフ）→ WGSL へ自動コンパイル。条件分岐は `where` 等の選択演算で表現し、スレッド分岐を排除。
- **数値**: 実装間ビット等価を主張する構成では、プロファイル A と同一の固定小数点フォーマットを用いなければならない（**MUST**）。
- **簡約の順序独立性**: DSL コンパイラは、非結合演算（浮動小数点加算等）を順序非決定な簡約へ写してはならない（**MUST NOT**、§2.3, §6.1）。
- **バックエンド差し替え**: ネイティブ WebGPU（主）／ Taichi・JAX（科学計算・ML 連携）／ NumPy（GPU 非搭載環境・CI フォールバック）。実装間ビット等価を主張する場合、全バックエンドが同一のビット演算制約を満たさなければならない（**MUST**）。
- **連携**: 履歴バッファを `numpy.ndarray` / PyTorch `Tensor` へゼロコピー（または最小コスト）でマッピングし、学習データへ接続。
- **I/O**: ステージングバッファの多重化による非同期転送でストールを回避。
- **エントロピー**: 共有メモリを用いた独立デーモンで収穫（§5）。

### 7.3 参照プロファイル C: CPU 参照実装（Conformance Baseline）

- **目的**: 仕様の**基準実装**。全機構を単純な逐次 CPU 実装で提供し、他プロファイルの実装間ビット等価を照合する基準とする。
- **数値**: 固定小数点演算を用い、**同一の再生同一性**（§4.9.2(a)）の下でプロファイル A / B と**ビット等価**な結果を出さなければならない（**MUST**）。
  - この照合は、A で生成したログを C で再生することで行う。**実装間ビット等価を主張する構成では実装識別子が再生同一性に含まれない**（§4.9.2）ため、この再生は正当である。
- **順序独立性の基準**: 逐次実装であっても、評価順序を置換した実行が同一結果を与えなければならない（**MUST**、§2.3）。これにより §9 の順序独立性検証の基準となる。
- **用途**: GPU 非搭載環境、テスト、監査。

> Full 適合を主張する実装は、代表シナリオでプロファイル C とのビット等価を検証しなければならない（**MUST**、§9）。

## 8. ドメインプロファイル（L4）— 参照例: ABC / VIF

ドメインプロファイルは、論理スキーマ・遷移規則・Dynamics 写像・エントロピー意味付けを与える。ABC は数ある適用先の**一例**であり、コアの一部ではない。

### 8.1 ABC 論理スキーマ（参照）

**基本表現（32bit）** — 各フィールドのビット割当:

| ビット | フィールド | 幅 | 意味 |
| --- | --- | --- | --- |
| `[0-1] / [2-3] / [4-5]` | `vA` / `vB` / `vC` | 各 2bit | 各軸の強度（Potential） |
| `[6-11] / [12-17] / [18-23]` | `dA` / `dB` / `dC` | 各 6bit（符号付） | 各軸の変動 $\Delta$（Excitation の源） |
| `[24-26]` | `State` | 3bit | 状態フラグ（有効／無効、高精度表現の有無 等） |
| `[27-29]` | `RuinScore` | 3bit | 累積劣化値（Accumulation） |
| `[30-31]` | `Reserve` | 2bit | 拡張用 |
| | **合計** | **32bit** | |

**高精度表現（64bit）** — 確定観測領域の中心付近や、変動の大きい領域の個体を一時的に昇格させる。

| ビット | フィールド | 幅 | 意味 |
| --- | --- | --- | --- |
| `[0-7] / [8-15] / [16-23]` | `vA` / `vB` / `vC` | 各 8bit | 強度（256 段階） |
| `[24-33] / [34-43] / [44-53]` | `dA` / `dB` / `dC` | 各 10bit（符号付） | 変動 $\Delta$（−512〜511） |
| `[54-56]` | `State` | 3bit | 状態フラグ |
| `[57-61]` | `RuinScore` | 5bit | 累積劣化値（32 段階） |
| `[62-63]` | `Reserve` | 2bit | 拡張用 |
| | **合計** | **64bit** | |

> **訂正記録**: v1.0.0 系および v2.0.0 は高精度表現を「強度 各8bit、$\Delta$ 各16bit」と記述していたが、これは $3\times8 + 3\times16 = 72\,\text{bit}$ となり 64bit に収まらない（`State`・`RuinScore` を加えると 78bit）。上表はビット予算内へ訂正したものである。

- **昇格・降格**: 精度が変われば軌跡が変わるため、昇格・降格は**シミュレーション適応**である。判定入力は確定状態由来に限らなければならない（**MUST**、§1 原則3）。
  - 観測領域・注視点を判定に用いる場合、それらは §4.4 の**観測者状態**として確定状態（権威化された入力 $A$）に含まれていなければならない（**MUST**）。表示専用カメラの注視点を用いてはならない（**MUST NOT**）。
  - 表現間の変換は決定論的でなければならない（**MUST**、§3.2）。
- **物理座標の分離**: 座標・速度は ABC パックとは別の固定小数点 SoA（16.16、高精度時 32.32）として保持し、精度とメモリ効率の要求を分離する。

### 8.2 ABC の Dynamics 写像

| Dynamics 契約（§6） | ABC での実装 |
| --- | --- |
| Potential（勢い） | ABC 強度 `vA` / `vB` / `vC` |
| Excitation（励起） | 変動 $\Delta$（`dA` / `dB` / `dC`） |
| Accumulation（蓄積） | `RuinScore`（不可逆劣化） |
| Interaction（相互作用） | 密集時のヤコビ反復（ダブルバッファ）。原子演算を併用する場合は整数加算・XOR 等の結合的演算に限る（§6.1） |

### 8.3 ABC のエントロピー意味付け（参照）

ABC ドメインは外部環境要因を **E0〜E3** の系統で表す（E0: 基底／外力なし、E1: 過酷環境、E2: 評価圧、E3: ノイズ）。§5 で収穫・正規化・権威化された環境ノイズを次のように写像する。

| 収穫源 | 写像先 |
| --- | --- |
| デバイス負荷（CPU 温度・バッテリ変動） | $E1$（過酷環境） |
| 環境ノイズ（マイク入力の dB 値・環境光） | $E3$（ノイズ） |
| 外部 API の変動 | $E2$（評価圧） |

- **終端個体の静的環境ソース化**: 終端状態（旧称 `Zero-Lock`／破綻）へ遷移した個体は動的計算から除外し、空間グリッド上の $E2$ / $E3$ の定数ソースへ転化する。これにより破綻が周囲の環境要因として再利用され、個体数の増加を伴わずに系へ影響を残す。

> 別ドメイン（粒子物理、群衆流動、経済シミュレーション等）は、同じ機構契約（§4）の上に**別の論理スキーマと Dynamics 写像**を差し込むだけで構築できる。これが本書の汎用性の核心である。

## 9. 適合性レベル（Conformance）

準拠実装は、達成レベルと、**実装間ビット等価を主張するか否か**を宣言しなければならない（**MUST**）。

| レベル | 必須要素・機構 | 想定用途 |
| --- | --- | --- |
| **Core** | §2.1 確定核、§2.3 決定論的遷移＋**順序独立性**、§3 論理スキーマ＋版、§4.4 入力、§6 Dynamics、§4.9.1–4.9.2 履歴（一次履歴＋再生同一性）、原則1 の**再現性** | 単一ノード・単一演算主体の決定論シミュレーション |
| **Standard** | Core ＋ §4.1 メモリ/LOD、§4.2 空間索引/階層、§4.3 スケジューラ、§4.5 露出制御、§4.6 出力 | 実時間の大規模単機シミュレーション／可視化 |
| **Full** | Standard ＋ §4.7 予測、§4.8 ネットワーク、§5 権威化、§4.9.4 数値決定論、原則1 の**実装間ビット等価** | 分散・P2P・自律介入を含む本格運用 |

> **§4.9.3 チェックポイントは全レベルで任意**（**MAY**）である。最適化であって仕様上の前提ではない（§4.9.3）。実装する場合は §4.9.3 に準拠しなければならない（**MUST**）。

### 適合性の検証

| 検証 | Core | Standard | Full |
| --- | --- | --- | --- |
| **再現性テスト**: 同一実装・同一再生同一性・同一シード・同一入力列で再計算し、ビット等価を確認 | **MUST** | **MUST** | **MUST** |
| **順序独立性検証**: 評価順序を置換（および並列分割を変更）しても確定状態列がビット等価に保たれること | **MUST** | **MUST** | **MUST** |
| **版検査**: 再生同一性が不一致のログの再生が拒否されること | **MUST** | **MUST** | **MUST** |
| **実装識別子検査**: ビット等価を主張**しない**構成で、別実装が生成したログの再生が拒否されること | 主張しない場合 **MUST** | 主張しない場合 **MUST** | — |
| **メタデータ非干渉**: ビット等価を主張**する**構成で、プロファイル識別子のみが異なるログの再生が拒否**されない**こと | 主張する場合 **MUST** | 主張する場合 **MUST** | **MUST** |
| **チェックポイント等価**: チェックポイントからの再開と、一次履歴からの全再計算が同一結果を与えること | 実装する場合 **MUST** | 実装する場合 **MUST** | 実装する場合 **MUST** |
| **適応分離検証**: **入力列（観測者状態を含む）を固定したまま**、実行時計測 $M(t)$ と表示層カメラのみを変化させたとき、確定状態列がビット等価に保たれること | — | **MUST** | **MUST** |
| **露出検証**: 非露出フィールドが出力・送出のいずれからも漏出しないこと | — | **MUST** | **MUST** |
| **LOD 保存**: LOD 段階を切り替えてもマクロ指標が宣言した許容誤差内で一致すること | — | **SHOULD** | **SHOULD** |
| **確定観測領域の一致**: 複数演算主体構成で、全観測者の観測領域の合併が全演算主体で一致すること | — | — | **MUST** |
| **基準実装照合**: 代表シナリオでプロファイル C とビット等価であること | — | **MAY** | **MUST** |

> **順序独立性検証**は §2.3 の要件を機械的に検査する。評価順序を置換して結果が変われば、非結合演算の順序非決定な累積（典型例: 浮動小数点の `atomicAdd`、§6.1）が混入している。逐次実装でも反復順序をシャッフルするだけで実施でき、**最も費用対効果の高い検証**である。
>
> **適応分離検証**は原則3 の区分（シミュレーション適応／表示適応）が守られているかを検出する。入力列を固定するのが要点で、これを固定せずカメラを動かすと、観測者状態が正しく確定状態に含まれている実装まで違反と誤判定してしまう。
>
> **実装識別子検査とメタデータ非干渉は排他**である。ビット等価を主張するか否かで、どちらか一方のみが適用される（§4.9.2）。

## 10. システムフロー（Standard 準拠の代表例）

1. **スキーマ生成**: 論理スキーマ → レイアウト／アクセサをコンパイル（§3.2）。再生同一性を確定（§4.9.2）。
2. **エントロピー確定**: 収穫→正規化→（複数演算主体構成なら権威化）し、Tick $N$ の $\varepsilon_N$ を確定して履歴へ記録（§5）。
3. **入力確定**: ユーザー入力と（シミュレーション適応に用いる場合は）**観測者状態**をリングバッファへ低アロケーションで取り込み、Tick へ割付・記録（§4.4）。複数演算主体構成では観測者状態も権威化（§5）。
4. **シミュレーション適応**: **確定状態由来の指標**（変動量、確定観測領域＝全観測者領域の合併 等）に基づき、シミュレーション LOD 段階・更新頻度・観測外カリングを決定し、実行対象を稠密化（§4.1, §4.3）。実行時計測 `M(t)` と表示層カメラはここでは用いない（§1 原則3）。
5. **階層演算**: トポロジカル順で親→子を決定論的に更新し、Dynamics を適用（§4.2, §6）。同一世代内は順序独立に評価する（§2.3）。
6. **（任意）未来探索**: 影響範囲内で、宣言した計算予算の範囲内で予測を実行（§4.7）。
7. **状態確定**: Tick ID で確定。複数演算主体構成では入力列の合意により不整合を再計算補正（§4.8, §4.9）。
8. **（任意）チェックポイント**: 実装する場合、宣言した間隔ごとに派生キャッシュを記録（§4.9.3）。
9. **露出判定**: 観測者ごとの露出集合を確定（§4.5）。
10. **出力**: 露出集合のみを読み取り専用アダプタで描画／エクスポート。**表示適応**（描画解像度・視錐台/遮蔽カリング）はここで `M(t)` と実行時カメラに基づき決定（§4.6, §1 原則3）。
11. **退避**: アクセス頻度に応じて Warm / Cold ストレージへ非同期退避（§4.1）。

> 手順4と手順10がこのフローの要である。**同じ「カリング」でも、手順4（観測外カリング）は確定状態を変えるため確定観測領域で駆動し、手順10（視錐台・遮蔽カリング）は出力のみのため実行時カメラで駆動する**。両者を1つのパスに統合してはならない（**MUST NOT**）。

## 12. まとめ

本書は、v1.0.0 系が実質的に「WebGPU × ABC 専用設計」であった点を検証し、**不変の抽象コア**と**差し替え可能な実行／ドメインプロファイル**へ層分離した。以降 v2.1.0 で12件、v2.2.0 で11件、v2.3.0 で7件、計30件の内部不整合を解消している（§0）。

- 形式モデルは「**確定状態を決定するか否か**」の単一基準により、**確定核5要素 $(S,A,C,D,\varepsilon)$ と観測層3要素 $(B,M,V)$** へ整理された。
- 決定論を**再現性**（全レベル必須）と**実装間ビット等価**（宣言制）へ分離し、単一ノード用途から異種ハードウェア分散までを、過剰な要求なしに一貫した枠組みで扱えるようにした。
- **順序独立性**を $C_D$ の明示要件とし、**原子演算を結合的演算に限定**した。純粋関数であることは並列簡約の順序独立性を含意しない — この区別の欠落は、v1.0.0 以来「ヤコビ反復と原子演算を並列に推奨する」形で潜伏していた最大の非決定性要因であった。
- **再生同一性を適合性依存の条件付き**とし、「実装間ビット等価を主張するなら実装識別子を含めない／しないなら含める」と対称化した。これにより、基準実装照合・混成メッシュの成立と、再現できない再生の拒否とを両立させた。
- **観測者状態**の導入により、v1.0.0 から継承されてきた決定論の穴（観測に基づく最適化が確定状態を観測者ごとに分岐させる）を塞いだ。観測に基づく最適化を行うなら、観測領域そのものが確定状態でなければならない。
- **一次履歴・再生同一性・チェックポイント**の三分により、可逆性は実際に再生可能で境界の明確な仕様へ強化された。チェックポイントは**最適化であって前提ではない**。
- **露出制御（Bank）** に機構契約を与え、信頼境界として出力・送出・予測の全経路に適用した。観測者状態が Bank の管轄外である帰結も明示した。
- WebGPU / WGSL / WebRTC / ABC は**参照プロファイル**へ退避し、CPU・他バックエンド・他ドメインへ適用可能とした。

資源制約を技術的優位へ転換するという UCD-F の思想は保ちつつ、その適用範囲を単一のドメイン・単一の実装から解放したものが本 Universal Core v2.3.0 である。
